# WG_Panel با تب نمایندگی و ظاهر فارسی/انگلیسی

سورس کامل [Azumi67/WG_Panel](https://github.com/Azumi67/WG_Panel) مبنای این مخزن است. برنامهٔ Flask، منوی لینوکسی، نصب، سرویس پنل، WireGuard، Node و تلگرام همان مسیرهای بومی هستند. تغییرات محصول به پوستهٔ سرمه‌ای/آبی فارسی/انگلیسی، تب نمایندگی و اصلاحات امنیتی ثبت‌شده محدود است.

نسخهٔ مرجع: `f0f41068e1fd453d17acad23b9b90bc2a284bf59`. مجوز در [LICENSE](LICENSE)، مستند اصلی در [README.upstream.md](README.upstream.md) و تفاوت‌ها در [SOURCE_PROVENANCE.md](SOURCE_PROVENANCE.md) حفظ شده‌اند.

## نصب تک‌خطی و منوی لینوکسی اصلی

این راهنما برای **VPS تازهٔ Debian/Ubuntu** است. همهٔ فرمان‌ها را با کاربر **root** اجرا کنید. اگر سرور را حذف یا Rebuild کرده‌اید، دسترسی SSH سرور قبلی خودکار به سرور جدید منتقل نمی‌شود.

### ۱. آماده‌سازی دسترسی SSH به گیت‌هاب

فرمان‌های زیر Git و ابزار SSH را آماده می‌کنند، در صورت نبودن کلید یک کلید جدید می‌سازند و **کلید عمومی** را نمایش می‌دهند. اگر کلیدی از قبل موجود باشد، بازنویسی نمی‌شود:

```bash
apt-get update && apt-get install -y git openssh-client
mkdir -p /root/.ssh && chmod 700 /root/.ssh
if [ -e /root/.ssh/id_ed25519 ] || [ -e /root/.ssh/id_ed25519.pub ]; then
  echo 'Existing SSH key found; it was not overwritten.'
else
  ssh-keygen -t ed25519 -N "" -C "wg-panel-vps" -f /root/.ssh/id_ed25519
fi
cat /root/.ssh/id_ed25519.pub
```

خروجی آخر که با `ssh-ed25519` شروع می‌شود را کپی کنید. در حساب گیت‌هابی که به این مخزن دسترسی دارد، صفحهٔ [افزودن کلید SSH](https://github.com/settings/ssh/new) را باز کنید، یک عنوان مانند `wg-panel-vps` بگذارید و کلید عمومی را ذخیره کنید. فایل `id_ed25519` کلید خصوصی است؛ فقط محتوای فایل دارای پسوند `.pub` را به گیت‌هاب بدهید.

برای بررسی اتصال، جداگانه اجرا کنید:

```bash
ssh -T git@github.com
```

پیام `successfully authenticated` نشان‌دهندهٔ اتصال موفق است؛ نداشتن دسترسی shell در همین پیام طبیعی است. اگر `Permission denied (publickey)` دیدید، کلید عمومی و دسترسی حساب به مخزن را بررسی کنید و سپس مرحلهٔ نصب را انجام دهید.

اگر کلید اختصاصی قدیمی شما `/root/.ssh/wg_panel_deploy` است و دسترسی مخزن دارد، به‌جای ساخت کلید جدید، پیش از فرمان نصب این خط را اجرا کنید:

```bash
export GIT_SSH_COMMAND='ssh -i /root/.ssh/wg_panel_deploy -o IdentitiesOnly=yes'
```

### ۲. دانلود و نصب با یک خط فرمان

پس از وصل‌شدن SSH گیت‌هاب، این فرمان آخرین سورس مخزن و تغییرات WG Portal را دریافت می‌کند و نصب‌کنندهٔ بومی همان سورس را باز می‌کند:

```bash
apt-get update && apt-get install -y git && git clone git@github.com:ashkanfthy97-alt/WG-Panel-Reseller.git /opt/wg-panel && cd /opt/wg-panel && bash wg.sh --wg-py /opt/wg-panel/wg.py
```

در **منوی اصلی `WG Panel Control`**، گزینهٔ **`2) Install / Setup`** و سپس **`2) Panel Quick Setup`** را انتخاب کنید و تنظیمات خواسته‌شده را وارد کنید. برای نصب کامل و مرحله‌به‌مرحله، به‌جای Quick Setup می‌توانید **`1) Install Everything`** را انتخاب کنید. نصب و سرویس همان WG_Panel بومی هستند؛ پیش‌نیازها طبق نصب‌کنندهٔ اصلی نصب می‌شوند.

بات هر نماینده را بعد از نصب، از داخل سایت با توکن و شناسهٔ عددی تنظیم کنید؛ گزینهٔ Telegram Quick Setup منوی لینوکس مربوط به بات اصلی مدیر است و برای بات نمایندگان لازم نیست.

مخزن خصوصی است؛ کلید SSH root باید مجوز خواندن آن را در GitHub داشته باشد. پوشهٔ `/opt/wg-panel` برای clone باید خالی/ناموجود باشد؛ دستور نصب، پوشه یا دادهٔ قبلی را حذف نمی‌کند. این مسیر برای نصب تازه است؛ برای پنل موجود از به‌روزرسانی استفاده کنید.

اگر سورس از قبل دریافت شده است، از داخل همان پوشه اجرا کنید:

```bash
bash wg.sh --wg-py "$PWD/wg.py"
```

`bash install.sh` و `bash install-gui.sh` نیز همین منوی ترمینالی را باز می‌کنند. فایل `installer/installer_web.py` در نسخهٔ مرجع وجود ندارد؛ برای نصب از منوی بومی `wg.sh` استفاده کنید.

## ورود و نمایندگی

آدرس و پورت پنل را در تنظیمات اصلی نصب تعیین می‌کنید؛ سرویس اصلی `wg-panel.service` خود `app.py` را اجرا می‌کند. برای ثبت مدیر اول، کد `SETUP_TOKEN` در مرحلهٔ تنظیم `.env` تولید/حفظ و فقط روی ترمینال نمایش داده می‌شود. ثبت و ورود مدیر از مسیرهای بومی `/register` و `/login` انجام می‌شود.

- داشبورد و صفحات عملیاتی از APIها، فرم‌ها و اسکریپت‌های خود WG_Panel استفاده می‌کنند.
- مدیر با تب `/resellers` نماینده می‌سازد و Interfaceهای مجاز، سقف Peer، توقف دسترسی و تمدید اعتبار را مدیریت می‌کند.
- نماینده در `/reseller` با هویت مستقل وارد می‌شود و فقط منابع خودش را می‌بیند. انقضای اعتبار دسترسی را متوقف می‌کند؛ مشتری یا کانفیگ حذف نمی‌شود.
- نمایندگی در **همان برنامه و سرویس پنل** اجرا می‌شود؛ به gateway، پورت ۸۷۶۵، setup جداگانه یا سرویس `wg-portal` نیاز ندارد.
- دادهٔ افزوده در `instance/resellers.sqlite3` نگهداری می‌شود. اگر فایل قدیمی `deploy/linux/runtime/resellers.sqlite3` موجود باشد، همان فایل استفاده می‌شود تا اطلاعات نمایندگی حفظ شود.

منوی بومی Update از همین fork دریافت می‌کند و فایل‌های محیط، دیتابیس‌ها و داده‌های runtime را حفظ می‌کند. برای نصب‌های موجود، قبل از تغییر سرویس‌ها از وضعیت و داده‌های همان سرور پشتیبان بگیرید.

## نصب قبلی با wg-portal

اگر نسخهٔ قبلی این مخزن را با `deploy/linux/install.sh` نصب کرده‌اید، سرویس‌های `wg-portal*` ممکن است هنوز روی سرور باشند. اصلاح سورس آن‌ها را متوقف، حذف یا مهاجرت نمی‌کند. فایل‌های آن نصب برای حفظ کار موجود باقی مانده‌اند و مسیر پیش‌فرض محصول نیستند. انتقال سرور موجود به سرویس بومی باید با بررسی پورت‌ها، واحدهای systemd، `.env` و مسیر دیتابیس همان سرور انجام شود؛ نصب تازه را کورکورانه روی آن اجرا نکنید.

## بررسی توسعه

```bash
python -B -m unittest discover -s tests -v
```

تست‌ها فقط فایل/دیتابیس موقت، APIهای شبیه‌سازی‌شده و loopback آزمایشی دارند؛ نصب‌کننده، apt یا سرویس واقعی اجرا نمی‌شود. نصب کامل بومی روی VPS در محیط توسعه اجرا نشده است. صفحات عملیاتی بومی و نمایندگی فارسی/راست‌چین هستند و تغییر زبان انگلیسی حفظ شده است. نام مشتری، متن سفارشی، مقادیر فنی و کانفیگ ترجمه نمی‌شوند؛ بررسی مرورگری صفحات با پاسخ‌های شبیه‌سازی‌شده انجام می‌شود.

## ورود نماینده، زیرنمایندگی و هزینهٔ ثبت

ورود همهٔ حساب‌ها از `/login` است؛ سرور مدیر یا نماینده را تشخیص می‌دهد و داشبورد مربوط را باز می‌کند. ورود دومرحله‌ای مدیر حفظ شده است. نمایندهٔ جدید پس از ورود، پنل انتظار تأیید پرداخت را می‌بیند: هزینهٔ هر نماینده ۵٬۰۰۰٬۰۰۰ تومان است؛ برای دریافت شماره کارت و تأیید پرداخت به [@AshkanfathiOfficial](https://t.me/AshkanfathiOfficial) پیام می‌دهد. فقط مدیر اصلی فعال‌سازی را تأیید می‌کند. تأیید اولیه یک‌بار ۳۰ روز اعتبار می‌دهد؛ تمدید بعدی همچنان از مدیر انجام می‌شود و تأیید پرداخت را دور نمی‌زند.

نمایندهٔ فعال می‌تواند از پنل خود زیرنماینده بسازد. Interface اختصاصی زیرنماینده از الگوی ذخیره‌شدهٔ مدیر ساخته می‌شود؛ سقف Peer از مقدار الگو و سقف والد بیشتر نمی‌شود. فعال‌سازی/تمدید زیرنماینده با مدیر اصلی است؛ توقف یا انقضای هر والد، دسترسی زیرمجموعه را متوقف می‌کند و داده‌ای حذف نمی‌شود.

در داشبورد مدیر، تعداد کل نمایندگان، تعداد زیرنمایندگان و جمع هزینه‌های ثبت نمایش داده می‌شود. در فهرست نمایندگان هم تعداد مستقیم و کل زیرمجموعهٔ هر حساب مشخص است. هزینهٔ ثبت هر نمایندهٔ جدید **۵٬۰۰۰٬۰۰۰ تومان، یک‌بار** است و پیش از ثبت نمایش داده می‌شود. این جمع، مبلغ ثبت‌شده است؛ وضعیت «پرداخت‌شده» یا تراکنش واقعی محسوب نمی‌شود و درگاه پرداخت اضافه نشده است.

طرح SQLite افزونه به نسخهٔ ۷ ارتقا یافته است: اطلاعات رمز‌شدهٔ دومرحله‌ای و رسیدهای تمدید بات به‌صورت افزایشی اضافه می‌شوند؛ ثبت عملیات ساخت Interface حساب‌های مستقیم مدیر به‌صورت افزایشی اضافه شده است؛ بستن حساب بدون حذف داده و رسیدهای ساخت انبوه اضافه شده‌اند؛ وضعیت تأیید و رزرو Interface به‌صورت افزایشی اضافه می‌شوند؛ حساب‌های قبلی تأییدشده باقی می‌مانند و ردیف‌ها، رمزها، اعتبار و مالکیت قبلی حفظ می‌شوند. این ارتقا هنگام اولین استفاده از کد جدید اعمال می‌شود؛ قبل از به‌روزرسانی سرور واقعی از دیتابیس نمایندگی پشتیبان بگیرید. کد جدید روی VPS توسط این تغییر اجرا نشده است.

## Interface اختصاصی و دسترسی محدود نماینده

نام نمایشی محصول WG Portal است؛ هسته و منوی نصب بومی WG_Panel حفظ شده‌اند. لوگوی ارسالی با پس‌زمینهٔ شفاف در `static/img/wg-portal-logo.png` قرار دارد.

در ساخت Interface، تنظیمات فنی Peer شامل Endpoint، Allowed IPs، DNS، MTU، Keepalive و Endpoint ثابت مشتری قابل تعیین است. برای Interface موجود از «پیش‌فرض‌های Peer اینترفیس» استفاده کنید. این پیش‌فرض‌ها برای Peerهای جدید اعمال می‌شوند؛ تنظیمات کانفیگ‌های قبلی خودکار بازنویسی نمی‌شود.

مدیر اصلی برای هر نماینده دقیقاً یک Interface تعیین می‌کند. حساب‌های قدیمی با چند Interface باید از فهرست نمایندگان به یک Interface تخصیص داده شوند؛ برنامه خودسرانه یکی را انتخاب نمی‌کند. نماینده مشخصات فنی Peer یا Interface حساب خودش را عوض نمی‌کند. نمایندهٔ فعال می‌تواند از تب افزودن نماینده زیرمجموعه بسازد و فقط برای زیرمجموعهٔ مستقیم و جدیدش Interface اختصاصی ایجاد کند. سیستم نام و شبکه و پیش‌فرض‌ها را تعیین می‌کند، پورت آزاد پیشنهاد می‌دهد و پورت مصرف‌شده یا رزروشده را رد می‌کند. ساخت Interface به‌تنهایی زیرنماینده را فعال نمی‌کند؛ تأیید مدیر اصلی همچنان الزامی است. تغییر تخصیص، Peer قدیمی را به Interface دیگری منتقل یا حذف نمی‌کند.

نماینده فقط نام، مدت و حجم Peer جدید را وارد می‌کند و برای Peer خودش تغییر نام یا تمدید انجام می‌دهد. دریافت کانفیگ/QR حفظ شده است. تمدید، روز و حجم را اضافه می‌کند؛ مصرف قبلی، کلیدها و تنظیمات فنی حفظ می‌شوند و رسید تکراری بستهٔ دیگری اضافه نمی‌کند. Peer نامحدود برای تغییر بسته به بررسی مدیر نیاز دارد.

تنظیمات افزوده در `instance/interface-peer-defaults.sqlite3` و رسیدهای تمدید در جدول افزایشی `portal_peer_renewals` دیتابیس بومی قرار می‌گیرند. قبل از انتشار روی سرور واقعی از دیتابیس‌ها و پوشهٔ instance پشتیبان بگیرید. تنظیمات Interface بین دیتابیس بومی و فایل افزوده ذخیره می‌شوند؛ در خطای ذخیرهٔ بخش دوم، پاسخ صریح «ذخیرهٔ جزئی» می‌گیرید و باید پس از رفع خطای دیسک/قفل دوباره ذخیره کنید.


## لینک کاربر و بات اختصاصی نماینده

در جدول مشتری‌های نماینده، کنار کانفیگ و QR گزینهٔ «لینک کاربر» صفحهٔ بومی همان مشتری را باز می‌کند؛ امکان کپی لینک هم وجود دارد. لینک و کانفیگ مشتری دیگر در دسترس نیست.

در بخش «بات اختصاصی نمایندگی»، توکن بات ساخته‌شده با BotFather و شناسهٔ عددی حساب تلگرام خودتان را وارد کنید و «ذخیره و راه‌اندازی خودکار» را بزنید. نصب دستی بات یا سرویس لینوکسی جداگانه لازم نیست؛ پردازش بات داخل سرویس خود پنل اجرا می‌شود و پس از راه‌اندازی مجدد پنل از سر گرفته می‌شود. در تلگرام بات را باز کنید و Start بزنید. پنل باید به api.telegram.org دسترسی خروجی داشته باشد؛ بات دارای Webhook یا بات اصلی مدیر تصاحب نمی‌شود. توکن را در گفتگو، اسکرین‌شات یا مخزن منتشر نکنید.

بات فقط در گفت‌وگوی خصوصی به شناسهٔ ثبت‌شده پاسخ می‌دهد. دستورها: `/new نام | روز | گیگابایت` برای ساخت، `/peers` برای فهرست، `/config شماره` برای کانفیگ، `/link شماره` برای لینک کاربر، `/rename شماره | نام` و `/renew شماره | روز | گیگابایت`. ساخت و تمدید از همان محدودیت‌ها و رسیدهای تکرارناپذیر پنل استفاده می‌کنند. وضعیت تأیید، اعتبار و توقف والد در هر عملیات بررسی می‌شود.

پس از ساخت کانفیگ یا انتخاب «کانفیگ‌های من»، هر مشتری چهار دکمه دارد: **کانفیگ، QR، لینک کاربر، نام/تمدید**. دکمهٔ آخر امکان تغییر نام یا افزودن روز و حجم را باز می‌کند. فرمان `/qr شماره` نیز تصویر QR و `/credit` اعتبار و ظرفیت خود نماینده را نشان می‌دهد. درخواست نام/تمدید پس از پنج دقیقه یا راه‌اندازی دوبارهٔ پردازش لغو می‌شود؛ دوباره دکمه را بزنید.

هر نماینده یک توکن مستقل دارد. دریافت پیام‌های بات‌ها با وظیفه‌های مستقل async انجام می‌شود؛ عملیات بومی در مخزن محدودی از پردازه‌های نخی اجرا می‌شود. تغییر توکن یا خطای یک بات، بررسی بات‌های دیگر را متوقف نمی‌کند. تعداد قابل استفاده به منابع سرور و محدودیت‌های تلگرام بستگی دارد؛ برای هر بات سرویس لینوکسی جدا نصب نمی‌شود. اتصال ناموفق اکنون خطای مشخصِ توکن، شبکه، اجرای تکراری، Webhook، محدودیت درخواست یا نشست امنیتی را نشان می‌دهد. حفاظت CSRF روی HTTPS حفظ شده است؛ درخواست تنظیم بات ارجاع هم‌مبدأ می‌فرستد.

توکن‌ها رمز‌شده در `reseller_bots.sqlite3` کنار دیتابیس نمایندگی ذخیره می‌شوند؛ کلید از کلید پایدار پنل مشتق می‌شود یا از FERNET_KEY تنظیم‌شده استفاده می‌کند. هنگام پشتیبان‌گیری، کلید پایدار پنل و هر دو دیتابیس را حفظ کنید. با «غیرفعال کردن بات» توکن ذخیره‌شده پاک می‌شود. این بات‌ها از هویت مدیر اصلی و فهرست مدیران بات سراسری استفاده نمی‌کنند.

## اعتبار و بخش مشترک سرویس‌ها

ساخت سرویس و فهرست مشتری‌ها و کانفیگ‌ها در تب «سرویس‌ها و کانفیگ‌ها» قرار دارند. لینک‌های قدیمی `#create-peer` و `#peers` به همین تب هدایت می‌شوند.

«بررسی اعتبار» از هر تب، پنجرهٔ زمان باقی‌مانده و سقف، مصرف، رزرو و تعداد باقی‌ماندهٔ Peer را باز می‌کند. زمان مؤثر، انقضای زودترِ حساب یا والد را در نظر می‌گیرد. درخواست ساختِ در حال انجام یا نامشخص، ظرفیت رزرو می‌کند؛ شمارش با قانون واقعی ساخت Peer یکسان است. حساب در انتظار یا متوقف هم وضعیت خودش را می‌بیند و اختیار ساخت نمی‌گیرد.


## ساخت خودکار Interface، ساخت انبوه و حذف

مدیر اصلی ابتدا در صفحهٔ نمایندگان، «پیش‌فرض ساخت Interface» را ذخیره کند: میزبان Endpoint بدون پورت، DNS، MTU، مسیرهای مجاز، Keepalive، محدودهٔ شبکه، اندازهٔ زیرشبکه، سقف Peer و قواعد فایروال. این الگو برای حساب مستقیم مدیر و هر سطح زیرنماینده استفاده می‌شود و در `instance/reseller-interface-defaults.json` ذخیره می‌شود و جزو پشتیبان داده‌های پنل است. پورت در الگو قابل تنظیم نیست.

مدیر برای ثبت نماینده نام کاربری، رمز و سقف Peer را وارد می‌کند و Interface انتخاب نمی‌کند. نماینده و زیرنماینده برای ثبت حساب زیرمجموعه فقط نام کاربری و رمز وارد می‌کنند. سرور شبکهٔ آزاد و پورت استفاده‌نشده از **51825 تا 52000** انتخاب و Interface اختصاصی را از مسیر بومی می‌سازد. نبودن الگوی مدیر یا پورت آزاد پیش از ثبت حساب گزارش می‌شود. نتیجهٔ نامشخص ساخت حفظ می‌شود؛ دوباره حساب نسازید و از مدیر بخواهید Interface واقعی را بررسی و تعیین کند. تعیین Interface به‌تنهایی حساب را فعال نمی‌کند؛ تأیید پرداخت جداست.

ساخت انبوه در تب سرویس‌ها و بات، ۱ تا ۲۰ Peer با پیشوند نام، مدت و حجم می‌سازد. نتیجهٔ موفق و ناموفق جدا نمایش داده می‌شود. رسید درخواست حفظ می‌شود؛ هنگام نتیجهٔ نامشخص، پیش از شروع مجموعهٔ جدید وضعیت قبلی را بررسی کنید.

حذف نماینده، دسترسی حساب و باتش را می‌بندد و مشتری‌ها، کانفیگ‌ها، زیرمجموعه‌ها و سابقه را نگه می‌دارد. زیرمجموعه تا بررسی مدیر دسترسی عملیاتی ندارد. حذف Peer گزینه و تأیید جدا دارد و از حذف بومی کانفیگ استفاده می‌کند؛ سهمیه فقط پس از تأیید حذف آزاد می‌شود.

منوی اصلی بات نماینده: **➕ ساخت PEER، 👥 ساخت نماینده، 📦 ساخت انبوه، ⚙️ تنظیمات**. ساخت‌ها مرحله‌ای‌اند و دکمهٔ لغو دارند. پس از ساخت، فایل کامل کانفیگ، تصویر QR و لینک کاربر فرستاده می‌شوند؛ متن کانفیگ و لینک کوتاه داخل کپشن HTML هر دو کارت، درست مانند بات بومی WG_Panel نمایش داده می‌شود. فقط پیش‌نمایش کپشن در پیام طولانی کوتاه می‌شود؛ فایل اصلی کامل است. منوها inline هستند و زیر کارت QR دکمه‌های Refresh، Edit و Back قرار دارند. تنظیمات فقط اعتبار، کانفیگ‌ها، زیرنماینده‌ها و وضعیت خود حساب را نشان می‌دهد.

در جدول «اتصال‌های اخیر» داشبورد مدیر، ستون «نماینده» صاحب هر Peer را نشان می‌دهد؛ زیرنماینده‌ها و حساب‌های بسته‌شده هم مشخص‌اند. مالک با شناسه و کلید عمومی تطبیق داده می‌شود. «بدون نماینده» یعنی نگاشت نمایندگی ثبت نشده و «نامشخص» یعنی دریافت اطلاعات مالک موفق نبوده است.


قالب کارت‌های بات بومی و بات نماینده از فایل مشترک `telegram_peer_cards.py` استفاده می‌کند. رد شدن تصویر QR توسط تلگرام باعث ارسال همان QR به‌شکل فایل می‌شود؛ خطای شبکه یا محدودیت تلگرام عملیات ساخت را تکرار نمی‌کند. اتصال هر بات همچنان فقط به حساب نمایندهٔ خودش دسترسی دارد.


## خروج، هزینهٔ جدید و امنیت نمایندگی

خروج از داشبورد نماینده، نشست نمایندگی را می‌بندد و به صفحهٔ ورود می‌رود؛ حتی هنگام انتظار برای درخواست دیگر قابل استفاده است. حساب‌های نمایندگی جدید در تمام سطوح **۵٬۰۰۰٬۰۰۰ تومان** هزینهٔ ثبت دارند. مبالغ ثبت‌شدهٔ حساب‌های قبلی تغییر نمی‌کنند و پنل انتظار پرداخت، مبلغ واقعی همان حساب را نشان می‌دهد.

در تب «امنیت و ورود دومرحله‌ای»، رمز فعلی را وارد کنید، QR را در برنامهٔ احراز هویت اسکن کنید و کد برنامه را برای فعال‌سازی بفرستید. کلید دستی نیز در همان مرحله نمایش داده می‌شود. کدهای بازیابی فقط یک‌بار نمایش داده می‌شوند؛ آن‌ها را خارج از پنل نگه دارید. هر کد بازیابی و هر کد زمانی پذیرفته‌شده فقط یک‌بار مصرف می‌شود. برای ورود بعدی، کد تازهٔ برنامه را در فیلد مشترک ورود مدیر/نماینده بزنید. غیرفعال‌کردن نیازمند رمز و کد معتبر است. فعال/غیرفعال‌سازی نشست‌های قبلی همان حساب را باطل می‌کند؛ نشست فعلی حفظ می‌شود. امنیت حساب حتی در زمان توقف اعتبار قابل مدیریت است.

بات **اصلی مدیر** در منوی بومی گزینهٔ «👥 نماینده‌ها» دارد: فهرست و زیرمجموعه‌ها، ساخت با اینترفیس خودکار، تأیید/لغو پرداخت، توقف/فعال‌سازی، تمدید، سقف Peer، بازیابی تخصیص اینترفیس، پیش‌فرض‌های ساخت، بستن حساب با حفظ منابع و بازنشانی دومرحله‌ای. عملیات حساس تأیید جدا می‌خواهند و تمدید دارای رسید تکرارناپذیر است. فقط مدیران فعلی بات اصلی در گفت‌وگوی خصوصی به این بخش دسترسی دارند؛ API key به‌تنهایی و هویت نماینده کافی نیستند.

کلید پایدار پنل و فایل `instance/resellers.sqlite3` را در پشتیبان نگه دارید؛ کلید دومرحله‌ای در دیتابیس رمز‌شده است. آرشیو حساب دسترسی را فوراً می‌بندد؛ اگر پاک‌سازی اطلاعات بات جداگانه شکست بخورد، نتیجهٔ واقعی همراه هشدار گزارش می‌شود و مشتری‌ها یا زیرمجموعه‌ها خودکار پاک نمی‌شوند.

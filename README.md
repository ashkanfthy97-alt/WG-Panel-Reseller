# WG_Panel با تب نمایندگی و ظاهر فارسی/انگلیسی

سورس کامل [Azumi67/WG_Panel](https://github.com/Azumi67/WG_Panel) مبنای این مخزن است. برنامهٔ Flask، منوی لینوکسی، نصب، سرویس پنل، WireGuard، Node و تلگرام همان مسیرهای بومی هستند. تغییرات محصول به پوستهٔ سرمه‌ای/آبی فارسی/انگلیسی، تب نمایندگی و اصلاحات امنیتی ثبت‌شده محدود است.

نسخهٔ مرجع: `f0f41068e1fd453d17acad23b9b90bc2a284bf59`. مجوز در [LICENSE](LICENSE)، مستند اصلی در [README.upstream.md](README.upstream.md) و تفاوت‌ها در [SOURCE_PROVENANCE.md](SOURCE_PROVENANCE.md) حفظ شده‌اند.

## نصب تک‌خطی و منوی لینوکسی اصلی

برای **نصب تازه** روی Debian/Ubuntu با کاربر root، پس از تنظیم دسترسی SSH به مخزن خصوصی:

```bash
apt-get update && apt-get install -y git openssh-client && (if [ -f /root/.ssh/wg_panel_deploy ]; then export GIT_SSH_COMMAND='ssh -i /root/.ssh/wg_panel_deploy -o IdentitiesOnly=yes'; fi; git clone git@github.com:ashkanfthy97-alt/WG-Panel-Reseller.git /opt/wg-panel && bash /opt/wg-panel/wg.sh)
```

این فرمان سورس را دریافت می‌کند و **منوی اصلی `WG Panel Control`** را باز می‌کند. در منو گزینهٔ `2) Install / Setup` و سپس `Install Everything` را انتخاب کنید تا مراحل نصب بومی، تنظیم `.env`، WireGuard، تنظیمات پنل، runtime، سرویس پنل و تلگرام انجام شود. می‌توانید مراحل اختیاری را رد کنید. پیش‌نیازها طبق اسکریپت اصلی نصب می‌شوند؛ نصب برای هر توزیع/نسخهٔ لینوکس تضمین نشده است.

مخزن خصوصی است؛ کلید SSH root باید مجوز خواندن آن را در GitHub داشته باشد. پوشهٔ مقصد برای clone باید خالی/ناموجود باشد؛ دستور بالا پوشهٔ قبلی را حذف نمی‌کند.

اگر سورس از قبل دریافت شده است، از داخل همان پوشه اجرا کنید:

```bash
bash wg.sh
```

`bash install.sh` و `bash install-gui.sh` نیز همین منوی ترمینالی را باز می‌کنند. فایل `installer/installer_web.py` در نسخهٔ مرجع وجود ندارد؛ برای نصب از منوی بومی `wg.sh` استفاده کنید.

## ورود و نمایندگی

آدرس و پورت پنل را در تنظیمات اصلی نصب تعیین می‌کنید؛ سرویس اصلی `wg-panel.service` خود `app.py` را اجرا می‌کند. برای ثبت مدیر اول، کد `SETUP_TOKEN` در مرحلهٔ تنظیم `.env` تولید/حفظ و فقط روی ترمینال نمایش داده می‌شود. ثبت و ورود مدیر از مسیرهای بومی `/register` و `/login` انجام می‌شود.

- داشبورد و صفحات عملیاتی از APIها، فرم‌ها و اسکریپت‌های خود WG_Panel استفاده می‌کنند.
- مدیر با تب `/resellers` نماینده می‌سازد و Interfaceهای مجاز، سقف Peer، توقف دسترسی و تمدید اعتبار را مدیریت می‌کند.
- نماینده در `/reseller` با هویت مستقل وارد می‌شود و فقط منابع خودش را می‌بیند. انقضای اعتبار دسترسی را متوقف می‌کند؛ مشتری یا کانفیگ حذف نمی‌شود.
- نمایندگی در **همان برنامه و سرویس پنل** اجرا می‌شود؛ به gateway، پورت ۸۷۶۵، setup جداگانه یا سرویس `wg-portal` نیاز ندارد.
- دادهٔ افزوده در `instance/resellers.sqlite3` نگهداری می‌شود. اگر فایل قدیمی `deploy/linux/runtime/resellers.sqlite3` موجود باشد، همان فایل استفاده می‌شود تا اطلاعات نمایندگی حفظ شود.

منوی بومی Update از همین fork دریافت می‌کند و فایل‌های محیط، دیتابیس‌ها و داده‌های runtime را حفظ می‌کند. برای نصب‌های موجود، قبل از تغییر سرویس‌ها از وضعیت و داده‌های همان سرور پشتیبان بگیرید.

## نصب قبلی با wg-portal

اگر نسخهٔ قبلی این مخزن را با `deploy/linux/install.sh` نصب کرده‌اید، سرویس‌های `wg-portal*` ممکن است هنوز روی سرور باشند. اصلاح سورس آن‌ها را متوقف، حذف یا مهاجرت نمی‌کند. فایل‌های آن نصب برای حفظ کار موجود باقی مانده‌اند و مسیر پیش‌فرض محصول نیستند. انتقال سرور موجود به سرویس بومی باید با بررسی پورت‌ها، واحدهای systemd، `.env` و مسیر دیتابیس همان سرور انجام شود؛ نصب تازه را کورکورانه روی آن اجرا نکنید.

## بررسی توسعه

```bash
python -B -m unittest discover -s tests -v
```

تست‌ها فقط فایل/دیتابیس موقت، APIهای شبیه‌سازی‌شده و loopback آزمایشی دارند؛ نصب‌کننده، apt یا سرویس واقعی اجرا نمی‌شود. نصب کامل بومی روی VPS در محیط توسعه اجرا نشده است. پوستهٔ فارسی/انگلیسی حفظ شده؛ ترجمهٔ همهٔ متن‌های قدیمی پنل کامل نیست.

## ورود نماینده، زیرنمایندگی و هزینهٔ ثبت

ورود همهٔ حساب‌ها از `/login` است؛ سرور مدیر یا نماینده را تشخیص می‌دهد و داشبورد مربوط را باز می‌کند. ورود دومرحله‌ای مدیر حفظ شده است. نمایندهٔ جدید پس از ورود، پنل انتظار تأیید پرداخت را می‌بیند: هزینهٔ هر نماینده ۳٬۰۰۰٬۰۰۰ تومان است؛ برای دریافت شماره کارت و تأیید پرداخت به [@AshkanfathiOfficial](https://t.me/AshkanfathiOfficial) پیام می‌دهد. فقط مدیر اصلی فعال‌سازی را تأیید می‌کند. تأیید اولیه یک‌بار ۳۰ روز اعتبار می‌دهد؛ تمدید بعدی همچنان از مدیر انجام می‌شود و تأیید پرداخت را دور نمی‌زند.

نمایندهٔ فعال می‌تواند از پنل خود زیرنماینده بسازد. Interfaceها و سقف Peer زیرنماینده از دسترسی والد بیشتر نمی‌شود. فعال‌سازی/تمدید زیرنماینده با مدیر اصلی است؛ توقف یا انقضای هر والد، دسترسی زیرمجموعه را متوقف می‌کند و داده‌ای حذف نمی‌شود.

در داشبورد مدیر، تعداد کل نمایندگان، تعداد زیرنمایندگان و جمع هزینه‌های ثبت نمایش داده می‌شود. در فهرست نمایندگان هم تعداد مستقیم و کل زیرمجموعهٔ هر حساب مشخص است. هزینهٔ ثبت هر نمایندهٔ جدید **۳٬۰۰۰٬۰۰۰ تومان، یک‌بار** است و پیش از ثبت نمایش داده می‌شود. این جمع، مبلغ ثبت‌شده است؛ وضعیت «پرداخت‌شده» یا تراکنش واقعی محسوب نمی‌شود و درگاه پرداخت اضافه نشده است.

طرح SQLite افزونه به نسخهٔ ۴ ارتقا یافته است: وضعیت تأیید و رزرو Interface به‌صورت افزایشی اضافه می‌شوند؛ حساب‌های قبلی تأییدشده باقی می‌مانند و ردیف‌ها، رمزها، اعتبار و مالکیت قبلی حفظ می‌شوند. این ارتقا هنگام اولین استفاده از کد جدید اعمال می‌شود؛ قبل از به‌روزرسانی سرور واقعی از دیتابیس نمایندگی پشتیبان بگیرید. کد جدید روی VPS توسط این تغییر اجرا نشده است.

## Interface اختصاصی و دسترسی محدود نماینده

نام نمایشی محصول WG Portal است؛ هسته و منوی نصب بومی WG_Panel حفظ شده‌اند. لوگوی ارسالی با پس‌زمینهٔ شفاف در `static/img/wg-portal-logo.png` قرار دارد.

در ساخت Interface، تنظیمات فنی Peer شامل Endpoint، Allowed IPs، DNS، MTU، Keepalive و Endpoint ثابت مشتری قابل تعیین است. برای Interface موجود از «پیش‌فرض‌های Peer اینترفیس» استفاده کنید. این پیش‌فرض‌ها برای Peerهای جدید اعمال می‌شوند؛ تنظیمات کانفیگ‌های قبلی خودکار بازنویسی نمی‌شود.

مدیر اصلی برای هر نماینده دقیقاً یک Interface تعیین می‌کند. حساب‌های قدیمی با چند Interface باید از فهرست نمایندگان به یک Interface تخصیص داده شوند؛ برنامه خودسرانه یکی را انتخاب نمی‌کند. نماینده مشخصات فنی Peer یا Interface حساب خودش را عوض نمی‌کند. نمایندهٔ فعال می‌تواند از تب افزودن نماینده زیرمجموعه بسازد و فقط برای زیرمجموعهٔ مستقیم و جدیدش Interface اختصاصی ایجاد کند. سیستم نام و شبکه و پیش‌فرض‌ها را تعیین می‌کند، پورت آزاد پیشنهاد می‌دهد و پورت مصرف‌شده یا رزروشده را رد می‌کند. ساخت Interface به‌تنهایی زیرنماینده را فعال نمی‌کند؛ تأیید مدیر اصلی همچنان الزامی است. تغییر تخصیص، Peer قدیمی را به Interface دیگری منتقل یا حذف نمی‌کند.

نماینده فقط نام، مدت و حجم Peer جدید را وارد می‌کند و برای Peer خودش تغییر نام یا تمدید انجام می‌دهد. دریافت کانفیگ/QR حفظ شده است. تمدید، روز و حجم را اضافه می‌کند؛ مصرف قبلی، کلیدها و تنظیمات فنی حفظ می‌شوند و رسید تکراری بستهٔ دیگری اضافه نمی‌کند. Peer نامحدود برای تغییر بسته به بررسی مدیر نیاز دارد.

تنظیمات افزوده در `instance/interface-peer-defaults.sqlite3` و رسیدهای تمدید در جدول افزایشی `portal_peer_renewals` دیتابیس بومی قرار می‌گیرند. قبل از انتشار روی سرور واقعی از دیتابیس‌ها و پوشهٔ instance پشتیبان بگیرید. تنظیمات Interface بین دیتابیس بومی و فایل افزوده ذخیره می‌شوند؛ در خطای ذخیرهٔ بخش دوم، پاسخ صریح «ذخیرهٔ جزئی» می‌گیرید و باید پس از رفع خطای دیسک/قفل دوباره ذخیره کنید.


## لینک کاربر و بات اختصاصی نماینده

در جدول مشتری‌های نماینده، کنار کانفیگ و QR گزینهٔ «لینک کاربر» صفحهٔ بومی همان مشتری را باز می‌کند؛ امکان کپی لینک هم وجود دارد. لینک و کانفیگ مشتری دیگر در دسترس نیست.

در بخش «بات اختصاصی نمایندگی»، توکن بات ساخته‌شده با BotFather و شناسهٔ عددی حساب تلگرام خودتان را وارد کنید و «ذخیره و راه‌اندازی خودکار» را بزنید. نصب دستی بات یا سرویس لینوکسی جداگانه لازم نیست؛ پردازش بات داخل سرویس خود پنل اجرا می‌شود و پس از راه‌اندازی مجدد پنل از سر گرفته می‌شود. در تلگرام بات را باز کنید و Start بزنید. پنل باید به api.telegram.org دسترسی خروجی داشته باشد؛ بات دارای Webhook یا بات اصلی مدیر تصاحب نمی‌شود. توکن را در گفتگو، اسکرین‌شات یا مخزن منتشر نکنید.

بات فقط در گفت‌وگوی خصوصی به شناسهٔ ثبت‌شده پاسخ می‌دهد. دستورها: `/new نام | روز | گیگابایت` برای ساخت، `/peers` برای فهرست، `/config شماره` برای کانفیگ، `/link شماره` برای لینک کاربر، `/rename شماره | نام` و `/renew شماره | روز | گیگابایت`. ساخت و تمدید از همان محدودیت‌ها و رسیدهای تکرارناپذیر پنل استفاده می‌کنند. وضعیت تأیید، اعتبار و توقف والد در هر عملیات بررسی می‌شود.

توکن‌ها رمز‌شده در `reseller_bots.sqlite3` کنار دیتابیس نمایندگی ذخیره می‌شوند؛ کلید از کلید پایدار پنل مشتق می‌شود یا از FERNET_KEY تنظیم‌شده استفاده می‌کند. هنگام پشتیبان‌گیری، کلید پایدار پنل و هر دو دیتابیس را حفظ کنید. با «غیرفعال کردن بات» توکن ذخیره‌شده پاک می‌شود. این بات‌ها از هویت مدیر اصلی و فهرست مدیران بات سراسری استفاده نمی‌کنند.
